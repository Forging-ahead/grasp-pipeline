# 调试顺序与验收证据

按下面的层次逐级通过。遇到错误先修当前层，保留请求、输入、实际状态和错误；不要通过减小碰撞几何、抬高成功容差或改原目标来制造成功。

## 分层验收

| 层次 | 要做的检查 | 通过标准与留存产物 |
| --- | --- | --- |
| G0 原生环境 | 只用 benchmark 自身 API 创建/重置/观测，核对任务、实际 seed、初态、原生成功和终止 | 原生环境独立可用；保存版本、初始状态/图像和 native status，observe 不增加动作 |
| G1 数据与来源 | 输出公开数据包，解析模型/网格资源，核对目标 ID、采集序号、任务原定义与观测模式 | Schema 通过；必需信息没有被 null/空场景或错误来源掩盖；通过本环境能力检查 |
| G2 坐标与模型 | 多个不同关节姿态下比对环境 FK 与规划模型；叠加 TCP、点云、目标区域、碰撞模型 | 记录各姿态位置/旋转误差、单位与允许容差；点云和碰撞位置一致，无重复偏移/缩放 |
| G3 空载执行 | 无目标接触时移动位置和朝向，单独测试夹爪 open/close/hold；核对底盘/另一手 | 每一步实际动作有记录，六自由度末端到位，限位和原生终止生效，保持夹爪不会意外松手 |
| G4 规划与预检 | 用工作空间内的自由目标、明确与障碍相交的给定路径测试；比较预演前后状态 | 可行路径被正常处理，碰撞路径被拒绝；预演不改变真实状态、时间或控制输入，预算退出有明确原因 |
| G5 单次抓取 | 检查 GraspGen 世界位姿、grasp→TCP 偏移、夹爪宽度、接近/闭合/抬升 | 夹爪确实接触目标，抬升证据与接触/状态一致；未触碰或未执行不能算模型抓取失败 |
| G6 完整抓放 | 用实测 TCP→物体关系计算搬运和放置目标，释放后稳定并查询原生目标 | 一条不中断回合，完整阶段及 native success 都有证据，失败视频和最后状态保留 |
| G7 关节及复合 | 逐个增加推移、开关、子目标依赖和物体/机构更新 | 单技能先验收；再验证完整任务和语言顺序，失败分类能定位到阶段 |
| G8 批量与交付 | 固定同版代码/配置，按明确任务清单与初态运行，记录所有状态 | 结果可复现，分母完整，unsupported/技术错误不被悄悄删除，见交付清单 |

G0–G4 不调用 GraspGen 也能排除大量环境、坐标、模型和控制问题。G5 才开始判断真实抓取效果。短视频可能只记录到了预检前的静态场景，必须同时看动作步数和失败阶段。

## 坐标检查要覆盖的量

1. 环境中的基座和 TCP 与规划模型是同一参考点；关节名称和顺序逐项核对。
2. 用已知物体/标志物核对深度反投影，检查图像和掩码上下翻转、光学轴和米制深度。
3. 检查 `world_T_grasp @ grasp_T_tcp`，偏移只应用一次；把物体中心当 TCP 或漏掉朝向都会导致未碰到目标。
4. 检查完整边长/半尺寸、mesh scale、物体局部/世界坐标，以及区域本地轴与重力方向。
5. 抓取后测量 `tcp_T_object`，若物体滑动或重抓，更新附件和场景。搬运与下降分别查询最新状态。

容差由实际机器人、控制器和配置决定，报告实际误差与阈值。当前 v10 的 0.097 m 偏移、0.15 m 抬升以及原控制容差只对原实现有依据，不作为新环境的统一校准值。

## 常见现象与优先排查

| 现象 | 先查哪里 |
| --- | --- |
| 图片有目标但点云为空 | 相机键、深度类型/量纲、实例 ID、掩码尺寸、上下翻转和可见点数 |
| 机器人没碰目标就退出 | 候选是否进入执行、真实动作数、起点有效性、TCP 参考点、姿态、限位与预检，不先归因生成器 |
| 明明有空间却没路径 | 保存起点、目标位姿、几何叠加、机器人模型/碰撞球、目标附件和阶段接触许可；区分目标不可达、起点无效和预算耗尽 |
| 到了位置但朝向不对 | ee 动作是否包含旋转、四元数顺序、基座变换、控制器尺度；仅 XYZ 的 move_to 不足以执行抓取位姿 |
| 抓起后掉落或被挤出 | 实测夹爪/物体相对关系、开口/力、hold 的原生语义、执行接触与加速度，不仅检查规划终点 |
| 放置超时或放不稳 | 容器区域和朝向、高度、持物几何、接触许可、跟踪误差与实际进展；保留规划拒绝和控制超时的区别 |
| 抽屉/门动不起来 | 把手、关节类型/轴/锚点、开关目标区间、持续接触和约束运动，不能只令末端直线去一个点 |
| 一段成功后后续对象位置变回去 | 是否每阶段重置环境，是否沿用过期场景或点云，是否预演恢复覆盖了真实新状态 |
| 进程退出码为 0 但任务失败 | 读取最终 RESULT/原生结果；工具或进程成功不等于完整任务成功 |
| Schema 通过但 readiness 拒绝 | 本环境能力是否实现、profile 是否匹配、资源/时间/区域是否齐全；不能只把 binding_status 改为 implemented |
| 两套环境服务和依赖相互影响 | 检查独立解释器、模型/规划进程环境、导入来源和实际 backend；不直接混装原三套依赖 |

## 可以现在执行的仓库检查

从代码根目录、在对应开发环境中：

```bash
python3 tools/verify_preservation.py
python3 tools/check_integration_docs.py
python tools/check_contracts.py --report migration/CONTRACT_VALIDATION.json
PYTHONPATH=src python -m pytest -q tests
```

第一项依赖冻结 v10 参考（可用 `--baseline` 指定位置）；第二项仅检查本轮文档；第三项使用 jsonschema 检查已有 LIBERO 样例；第四项需要原 CPU 测试依赖（NumPy、SciPy、MuJoCo、robosuite 资产等）。缺依赖或跳过测试应如实报告。

上述检查不能替代新环境的 G0–G8。接入方需要在自己新增的入口/测试中完成真实运行，保留一条通过和一条可解释失败的证据；当前仓库没有现成的 RoboTwin/RoboCasa smoke-test 命令。
